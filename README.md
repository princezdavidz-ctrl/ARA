# ARA — Autonomous Respond Agent

NestJS + TypeScript backend for ARA, a multi-company AI communication platform. The existing agency workspace is the tenant foundation; the platform expansion adds separate platform administration, company-specific AI configuration, channel connections, and hybrid subscription metering.

## Setup
1. Copy .env.example to .env; set OpenAI key, 32+ character ingestion key and JWT secret.
2. Start PostgreSQL with docker compose up -d db.
3. Apply SQL migrations 001_init.sql through 014_industry_neutral_knowledge.sql in numeric order. Migrations 011–014 add the multi-company platform foundation, webhook verification tracking, per-conversation channel-connection ownership, and industry-neutral knowledge bases/categories. Payment processing and the separate frontend applications remain future implementation work.
4. Run npm ci, npm run build, npm test, then npm run start:dev.

## Platform architecture\nThe approved architecture and implementation sequence are documented in [docs/PLATFORM_ARCHITECTURE.md](docs/PLATFORM_ARCHITECTURE.md). ARA uses shared AI infrastructure with isolated company knowledge and configuration, supervised replies, hybrid subscription plus usage billing, and separate Super Admin and Company CRM applications.\n\n## ARA Super Admin API (foundation)\nMigration 011 adds a separate platform-admin identity. To bootstrap the first Super Admin, apply migrations through 011, set `ARA_BOOTSTRAP_PLATFORM_ADMIN_EMAIL`, `ARA_BOOTSTRAP_PLATFORM_ADMIN_NAME`, and a unique `ARA_BOOTSTRAP_PLATFORM_ADMIN_PASSWORD` (minimum 16 characters) in the deployment secret manager, then start the API once. The bootstrap creates an administrator only when the platform-admin table is empty and removes the password variable from the process environment. Remove the bootstrap secret from the deployment configuration after successful initialization. Do not use a company CRM access token for these endpoints.\n\n- `POST /admin/auth/login` — platform administrator login.\n- `GET /admin/overview` — platform overview metrics.\n- `GET /admin/companies` — paginated/searchable company list (`limit`, `offset`, `q`).\n- `GET /admin/companies/:id` — company profile and subscription summary.\n- `POST /admin/companies` — create a company and its first owner in one transaction. Requires `companyName`, `industry`, `ownerFullName`, `ownerEmail`, and a temporary password (12+ characters).\n- `PATCH /admin/companies/:id/status` — activate/deactivate a company with an audited action.\n\nAll routes except login require a platform token in `Authorization: Bearer`. Company lifecycle mutations require the `super_admin` role. These endpoints are an initial API foundation; rate limiting, MFA, password reset, invitation delivery, and a production Super Admin web UI remain required before broad production access.\n\n## Company channel connections\nCompany owners and admins can manage tenant-scoped channel connection records through `GET /platform/channels`, `POST /platform/channels`, `PATCH /platform/channels/:id/credentials`, `PATCH /platform/channels/:id/status`, and `POST /platform/channels/:id/verify`. Credentials are encrypted with AES-256-GCM before storage and are never included in API responses. Set `ARA_CHANNEL_ENCRYPTION_KEY` to a stable 32-byte key (generate using `openssl rand -hex 32`) and keep it in a secret manager; `ARA_CHANNEL_ENCRYPTION_KEY_VERSION` labels the active key version. New records remain `pending` until a company owner/admin submits `accessToken` and `webhookVerifyToken`, then calls the verify endpoint. For WhatsApp, set `externalAccountId` to the WhatsApp Business Account ID and `externalPhoneNumberId` to the phone-number ID. For Instagram, set `externalAccountId` to the Instagram professional account ID. The verify endpoint checks the access token against Meta Graph API before activating the connection. WhatsApp and Instagram inbound webhooks can now resolve active database-backed connections by provider account ID, while the legacy single-company environment variables remain a compatibility fallback. Store a unique `webhookVerifyToken` alongside each Meta connection's credentials so Meta can verify the shared webhook URL. Meta signature verification still uses the platform-level app secret. Email and TikTok connections are also tenant-routed: set `externalAccountId` to the receiving email address (or the account identifier used by your relay) for email, and the authorized TikTok Business account ID for TikTok. Store `webhookSecret` in each connection's encrypted credentials; email additionally requires `apiKey` and `fromAddress`, while TikTok requires `accessToken`. The signed inbound relay resolves the active connection by recipient/account before validating its tenant-specific secret. Email, TikTok, WhatsApp and Instagram conversations retain the exact connection ID and their outbound replies use that connection's encrypted credentials. Legacy environment-based routing remains available for old conversations and single-company deployments.\n\n## Industry-neutral knowledge and supervised AI
ARA knowledge is no longer limited to real-estate categories. The `category` field accepts a lowercase category slug (1–64 characters), and each document is assigned to a tenant-owned knowledge base. Existing company documents are migrated into the default Company Knowledge base. New company registrations receive company settings, supervised AI defaults, and a default knowledge base.

- `GET /knowledge/bases` lists the authenticated company's knowledge bases.
- `GET /knowledge/templates` returns recommended knowledge categories for the company's configured industry plus general categories.
- `POST /knowledge` accepts `title`, `category`, `language`, `content`, optional `sourceRef`, optional `knowledgeBaseId`, and arbitrary JSON `metadata`.
- `POST /answer` supports optional `filters.category`, `filters.knowledgeBaseId`, and JSON `filters.metadata`. Existing real-estate filters remain supported for compatibility.

Company AI settings now guide the answer policy: the company industry, agent name, supplemental instructions, confidence threshold, response mode, enabled flag, and sensitive-topic escalation preference are loaded per tenant. Evidence remains mandatory and model citations must refer to retrieved tenant documents. When AI is disabled, draft-only approval is configured, evidence is missing, confidence is below threshold, or the model output fails grounding checks, the worker creates a human escalation and does **not** send the AI draft to the customer. Only validated `answered` responses enter outbound delivery.

## Property and lead management
Authenticated agency users can manage tenant-scoped property inventory and lead pipelines through the /platform/properties and /platform/leads endpoints. Property records are indexed into the agency RAG knowledge base. Listing availability and pricing must be kept current by agency staff.

## Agency dashboard
Open /dashboard after starting the API. The browser workspace supports agency login, overview metrics, leads, property inventory, conversations and team directory. It uses authenticated platform APIs. Conversation messages show their current delivery status; queued is not proof of delivery.

## Message processing and WhatsApp
Inbound text messages are processed by the tenant-scoped RAG worker. AI replies and human outbound messages for WhatsApp conversations are sent through Meta's WhatsApp Cloud API when WHATSAPP_ACCESS_TOKEN and WHATSAPP_PHONE_NUMBER_ID are configured. Without these values, messages remain queued for handling in the dashboard; WhatsApp is optional.

The worker marks a message sent only after Meta accepts it and returns a message ID. This is API acceptance, not confirmed recipient delivery; webhook delivery receipts are not yet reconciled. Transient failures retry with exponential backoff for up to five attempts; permanent 4xx errors other than 429 are marked failed. Meta's customer-service window and template-message rules apply, so Meta can reject free-form messages outside the permitted window. A worker crash after Meta accepts a message but before ARA saves the response can cause a duplicate on retry (at-least-once delivery).

Inbound webhook setup remains separate and requires WHATSAPP_AGENCY_ID, WHATSAPP_PHONE_NUMBER_ID, WHATSAPP_VERIFY_TOKEN and WHATSAPP_APP_SECRET. It maps one configured WhatsApp phone number to one agency, verifies Meta's challenge and HMAC signature, deduplicates webhook message IDs, and queues inbound text. Non-text media is escalated for human review and is not interpreted.

## Production status
The worker runs inside the API process; use one worker-enabled instance or add a dedicated worker lease before horizontal scaling. Apply migrations and run build, unit, integration and security tests before production. Use HTTPS, rate limiting, secrets management, backups and monitoring.

## Email channel
ARA supports email conversations using Resend for outbound delivery and a signed inbound relay endpoint. For legacy single-company mode, configure EMAIL_AGENCY_ID, EMAIL_RESEND_API_KEY, EMAIL_FROM_ADDRESS and EMAIL_WEBHOOK_SECRET together. For tenant connections, create an `email` channel connection with `externalAccountId` set to the receiving address and encrypted credentials `webhookSecret`, `apiKey` (Resend API key) and `fromAddress` (verified sender). Leave legacy values blank when using only tenant connections. The sender address must be verified with Resend.

Inbound email relays POST JSON to /webhooks/email with headers X-ARA-Email-Timestamp (Unix seconds) and X-ARA-Email-Signature (sha256=HMAC-SHA256(secret, timestamp + "." + raw request body)). Timestamps must be within five minutes. The JSON contract includes the receiving mailbox so ARA can select the tenant connection before validating its signature: { "to": "support@company.example", "from": { "email": "customer@example.com", "name": "Customer" }, "subject": "Property enquiry", "text": "Message body", "messageId": "unique-provider-message-id" }. The value of `to` must match the email channel connection's `externalAccountId`. The relay must verify the upstream provider's webhook and then sign the normalized body using this ARA signature. Inbound IDs are deduplicated and tenant-scoped. ARA generates a grounded response using the same RAG worker and sends it as an email reply; human replies can be queued through the existing conversation message API, optionally with a subject.

Email retries use the same maximum-five-attempt exponential backoff and provider idempotency key. ARA marks an email sent only after Resend accepts it and returns an ID; this is not proof of inbox delivery. Provider-specific inbound relay setup and delivery/read receipts are separate integration work.

## Instagram Direct Messages
Instagram inbound messages are accepted at /webhooks/instagram after Meta's hub.challenge verification and X-Hub-Signature-256 validation. Configure INSTAGRAM_AGENCY_ID, INSTAGRAM_ACCOUNT_ID, INSTAGRAM_ACCESS_TOKEN, INSTAGRAM_APP_SECRET and INSTAGRAM_VERIFY_TOKEN together. The linked Instagram professional account and Meta app must have the required messaging permissions and production review. A customer must initiate the conversation; the standard messaging window applies. Replies are sent through Instagram's Messaging API and retried up to five times. Attachments are recorded and escalated for human review.

## TikTok Business Messaging
TikTok inbound messages are accepted at /webhooks/tiktok and normalized from DIRECT_MESSAGE webhook content. For legacy single-company mode, configure TIKTOK_AGENCY_ID, TIKTOK_BUSINESS_ID (the authorized business account ID), TIKTOK_ACCESS_TOKEN and TIKTOK_WEBHOOK_SECRET together. For tenant connections, create a `tiktok` channel connection with `externalAccountId` set to the authorized business account ID and encrypted credentials `webhookSecret` and `accessToken`. The TikTok developer app must be approved for Business Messaging and the business account must authorize it. The endpoint expects X-ARA-TikTok-Timestamp (Unix seconds) and X-ARA-TikTok-Signature (sha256=HMAC-SHA256(secret, timestamp + "." + raw request body)); a provider relay should validate TikTok's native webhook and sign the normalized payload for ARA. The normalized payload contains event_type=DIRECT_MESSAGE and content with conversation_id, message_id, from_user.open_id, message_type and text.body. Replies use TikTok's official Business Messaging send endpoint and conversation_id. TikTok messaging windows and quota rules apply; users must initiate contact. Access tokens are short-lived and must be refreshed by the operator; automated OAuth token refresh is not yet implemented.
